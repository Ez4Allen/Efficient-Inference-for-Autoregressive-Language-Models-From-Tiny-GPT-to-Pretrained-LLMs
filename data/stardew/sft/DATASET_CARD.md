# Stardew Valley SFT Candidate Pool -- Dataset Card

## What this is

This is an **AI-assisted SFT candidate pool**, not the official Stardew
Valley benchmark and not a certified human-verified training set. It is a
starting point for future human review, not a finished deliverable.

The official, reviewer-approved Stardew Valley benchmark lives under
[`data/stardew/evaluation/`](../evaluation/) (`stardew_validation_v1.jsonl`,
`stardew_eval_v1.jsonl`) and follows a separate two-person review process
described in `data/stardew/Stardew_Valley_Knowledge_Module_Task_EN.md`
section 13. Do not substitute this candidate pool for that benchmark.

## Data lifecycle

```text
data/stardew/candidates.jsonl                  (raw, immutable, never edited in place)
        |
        v   scripts/clean_stardew_sft_data.py  <-- data/stardew/sft/review_log.jsonl (human decisions)
data/stardew/sft/candidates.normalized.jsonl   (all records, controlled schema)
        |                                       + data/stardew/sft/rejected.jsonl
        |                                       + data/stardew/reports/sft_cleaning_report.json
        v   scripts/split_stardew_sft_data.py
data/stardew/sft/{train,validation,eval}.jsonl (release splits)
                                                 + data/stardew/reports/sft_split_manifest.json
```

* `data/stardew/candidates.jsonl` is the original 1,262-record AI-assisted
  pool exactly as first generated. It is preserved unmodified for
  provenance; nothing in this pipeline writes to it.
* `data/stardew/sft/review_log.jsonl` is the durable, git-tracked record of
  human review decisions, keyed by `legacy_id`. Each entry requires
  `decision` (`approved` / `rejected` / `needs_changes`), `reviewer`, and
  `reviewed_at` -- an entry without reviewer/timestamp attribution is
  rejected at load time. **Do not hand-edit `candidates.normalized.jsonl`
  to record a review decision** -- it is regenerated by the cleaning script
  and any such edit is silently lost on the next run; add a line to the
  review log instead, which survives re-runs.
* `scripts/clean_stardew_sft_data.py` reads the raw pool and produces a
  **normalized candidate pool** (`candidates.normalized.jsonl`, all 1,262
  input records, one output row each) with: a controlled reporting
  taxonomy, canonicalized source pages, deterministic `knowledge_group`
  assignment, an automated structural/duplicate pass, and -- if
  `review_log.jsonl` exists -- human review decisions applied on top,
  overriding the automated pass. It never invents or discards data
  silently -- every dropped record is still present in `rejected.jsonl`
  with a reason.
* `scripts/split_stardew_sft_data.py` reads the normalized pool, excludes
  `review_status == "rejected"` records, and partitions the rest into
  `train.jsonl` / `validation.jsonl` / `eval.jsonl` by `knowledge_group` so
  that no wiki page or near-duplicate question family crosses a split
  boundary.
* `scripts/audit_stardew_sft_data.py` produces a deterministic, code-generated
  count report over any set of split files. It was run before cleanup
  (`data/stardew/reports/sft_audit_v1.{json,md}`) and after
  (`sft_audit_v2.{json,md}`) using the identical methodology, so the two
  are directly comparable.

## Review status: reviewed and approved (bulk, 2026-08-05)

Every record in the original pool carried `verified: true` and
`reviewed_by: "maggie"`, but there was no auditable per-record review log
(no reviewer, timestamp, or notes) behind that claim. A boolean flag is not
evidence someone opened the source and checked every fact -- it is exactly
the kind of claim this pipeline exists to stop trusting blindly.

On 2026-08-05, reviewer `maggie` reviewed the 129 records that fell into
`task_family: "other"` (the unmapped-category set) for taxonomy fit, found
no blocking issues there, and made a bulk decision to approve the rest of
the pool without an additional per-record fact-check beyond the automated
pipeline checks; that decision, and 4 additional records rejected as
duplicate answers the automated exact-match check had missed, are recorded
in `data/stardew/sft/review_log.jsonl` with reviewer/timestamp attribution
and applied by `scripts/clean_stardew_sft_data.py`. **This was a bulk
approval, not an individual per-record source fact-check** -- see Known
limitations.

Records fall into one of these `review_status` values:

| Status | Meaning | Count |
|---|---|---:|
| `approved` | Carries `reviewer` + `reviewed_at` (+ optional `review_notes`) tying the record to a real review event. | 1,253 |
| `rejected` | Excluded from the release splits; see `rejected.jsonl` for the reason. | 9 |
| `pending` | No review evidence yet (default state for anything not covered by a review-log entry or the automated pass). | 0 |
| `needs_changes` | A human reviewer flagged the record for rework rather than approving or rejecting outright. | 0 |

`verified` is `true` only when `review_status == "approved"`. The original
`reviewed_by: "maggie"` value is preserved as `legacy_reviewed_by` for
traceability, but it is legacy metadata only -- it is not proof of the
*original* AI-generation-time claim and is distinct from the new, attributed
`reviewer` / `reviewed_at` / `review_notes` fields.

**Practical effect:** `scripts/validate_sft_data.py --strict` now passes
(0 errors) against the release splits, because every kept record carries
real reviewer attribution. Before this review pass it correctly failed --
strict mode is a gate for a certified release, and an unattributed pool is
not one.

## Taxonomy: `task_family`, `topic`, `intent`

The raw pool used ~490 free-form `category` labels (e.g. `crafting_recipe`,
`crafting_recipes`, `tailoring_dyeing`, `tailoring_and_dyeing`,
`dyeing_tailoring` all describing overlapping ideas), which makes reliable
filtering or balancing impractical. Each record now also carries:

* `original_category` -- the untouched raw category string, kept for
  traceability.
* `topic` -- the normalized (lowercased) original category, fine-grained.
* `task_family` -- a small controlled bucket for reporting:
  `crop_planning`, `fish_availability`, `villager_gifts`,
  `recipe_ingredients`, `bundle_community_center`, `item_acquisition`,
  `guide_progression`, `other`.
* `intent` -- kept compatible with
  [`src/games/stardew/intent_router.py`](../../../src/games/stardew/intent_router.py)'s
  existing vocabulary rather than inventing a parallel intent system.

The mapping is one ordered, versioned rule table:
[`src/games/stardew/sft_taxonomy.py`](../../../src/games/stardew/sft_taxonomy.py)
(`TAXONOMY_VERSION`). A category that matches no rule falls back to
`task_family: "other"` / `intent: "unknown"` and is counted in
`sft_cleaning_report.json`'s `unmapped_category_counts` rather than being
guessed silently. As of this cleanup, 129 of 1,262 records (98 distinct
categories) fall into `other` -- miscellaneous mechanics (combat, mines,
weather, UI, outfits, farm buildings) that do not fit the eight-family
scheme. `item_acquisition` is by far the largest family (591 records, 47%)
because the pool heavily favors "how do I obtain X" style questions across
furniture, weapons, hats, and other collectibles; see Known limitations.

## Source canonicalization

Wiki citations in the raw pool used inconsistent capitalization for the
same page (e.g. `Slime_Incubator` vs `Slime_incubator`). Left alone, this
undercounts true source-page reuse and lets a naive page-based splitter
place two records from the same page in different splits.
[`src/games/stardew/sft_sources.py`](../../../src/games/stardew/sft_sources.py)
normalizes each `source_urls` entry (scheme/host validated to
`stardewvalleywiki.com`, fragment and query stripped, percent-decoded,
space/underscore unified) into a case-insensitive grouping key, then picks
one canonical display title per key across the *whole corpus*
(lexicographically smallest observed variant, deterministic). The result is
`source_pages` (canonical) alongside the untouched `source_urls`
(provenance). No redirect target, section title, revision ID, or game
version is ever invented -- only literal URL text is normalized.

## Duplicate and template-leakage handling

Two distinct signals are used, deliberately kept separate:

1. **Exact/near-exact duplicates (auto-rejected):** a record whose
   normalized question or normalized answer exactly matches an earlier
   record's is rejected (`duplicate_question` / `duplicate_answer`) and
   moved to `rejected.jsonl`. The automated pass rejected 5 records this
   way -- all `duplicate_answer` cases caused by the same source page being
   cited under two different capitalizations before canonicalization. A
   further 4 were rejected by human review as duplicate answers the
   automated exact-match check missed (see `review_log.jsonl`), for 9
   total (see `sft_cleaning_report.json`).
2. **Template-shape leakage (flagged, not auto-rejected):** entity-masked
   question comparison (numbers, seasons, and the record's own source-page
   name replaced with placeholders) surfaces cases where two records ask
   the "same shape" of question about different entities. These are
   reported in `sft_cleaning_report.json`'s `template_leakage_pairs` for
   human review, per the project's "flag, don't blindly delete" rule --
   auto-merging every template-similar pair by knowledge group was tried
   and rejected during this cleanup because it collapsed most of
   `item_acquisition` into a single knowledge group and produced a
   validation split larger than train. See Known limitations.

The splitter groups records by `knowledge_group`, which unions (a) records
citing an overlapping canonical source page and (b) records whose
*unmasked* question text is itself near-duplicate (similarity >= 0.90) --
i.e. it prevents genuine paraphrase leakage across splits without
forcing every same-shaped question about different entities into one
group.

threshold. It is not factual leakage; it is listed here rather than hidden.
See Known limitations.

## Known limitations / items requiring human review

* **The 2026-08-05 review was a bulk approval, not an individual
  per-record source fact-check.** Reviewer `maggie` checked the 129
  unmapped-category records for taxonomy fit and manually found 4 more
  duplicate answers; the remaining ~1,120 records were approved as a
  blanket decision without individually re-verifying each answer against
  its wiki source. `verified: true` here means "reviewed and released by
  a named, dated reviewer," not "every fact was independently
  re-checked." Treat this pool as reviewed-and-released candidates, not as
  equivalent in rigor to the two-person-reviewed formal benchmark under
  `data/stardew/evaluation/`.
* **English only.** No Chinese-language coverage, unlike the formal
  evaluation benchmark's bilingual requirement.
* **Source coverage bias.** 405 canonical pages back 1,253 records --
  some pages (e.g. `Statue_Of_Perfection`-family pages) are cited far more
  than others.
* **Category imbalance.** `item_acquisition` accounts for 47% of records;
  `bundle_community_center` accounts for well under 1%.
* **Template repetition.** The pool leans heavily on a small number of
  generic question phrasings ("How can a player obtain X in Stardew
  Valley?", "What can X be used for in tailoring?") applied to many
  different entities. `sft_cleaning_report.json` lists every flagged pair;
  a human should decide which are worth rewriting for phrasing diversity
  in a future PR. This cleanup deliberately did not generate new questions
  to fix this -- that is out of scope for PR1.
* **129 records (98 categories) fall into the `other` task family** and
  were not force-fit into one of the eight recommended families; a human
  familiar with the category list should sanity-check
  `unmapped_category_counts` in the cleaning report.
* **Every legacy record ID baked the literal string `"train"` into it**
  regardless of which split the record actually ended up in (e.g. a record
  living in `validation.jsonl` had an ID containing `..._train_..._0343`).
  New IDs (`sdv_sft_000001` etc.) no longer encode a split, and
  `legacy_id` preserves the original for traceability.

## Commands

Regenerate the baseline/comparison audit for any split files:

```bash
python scripts/audit_stardew_sft_data.py \
  --split train=data/stardew/sft/train.jsonl \
  --split validation=data/stardew/sft/validation.jsonl \
  --split eval=data/stardew/sft/eval.jsonl \
  --output-json data/stardew/reports/sft_audit_v2.json \
  --output-md data/stardew/reports/sft_audit_v2.md \
  --title "Stardew SFT candidate pool -- post-cleanup audit"
```

Re-run cleaning (raw candidates + `review_log.jsonl` -> normalized pool +
rejected.jsonl; the review log is applied automatically if present at its
default path):

```bash
python scripts/clean_stardew_sft_data.py \
  --input data/stardew/candidates.jsonl \
  --outdir data/stardew/sft \
  --report data/stardew/reports/sft_cleaning_report.json \
  --review-log data/stardew/sft/review_log.jsonl
```

To record a new review decision, append a line to
`data/stardew/sft/review_log.jsonl` (one JSON object per line):

```json
{"legacy_id": "stardew_valley_train_x_0001", "decision": "approved", "reviewer": "your_name", "reviewed_at": "2026-08-06", "review_notes": "Checked against the wiki table."}
```

then re-run the cleaning command above, followed by the splitter. Do not
edit `candidates.normalized.jsonl` directly -- it is regenerated output.

Re-run the group-aware splitter (normalized pool -> train/validation/eval):

```bash
python scripts/split_stardew_sft_data.py \
  --input data/stardew/sft/candidates.normalized.jsonl \
  --outdir data/stardew/sft \
  --manifest data/stardew/reports/sft_split_manifest.json \
  --val-frac 0.1 --eval-frac 0.1 --seed 42
```

Validate the release splits (both non-strict and strict now pass, since
every kept record carries reviewer attribution):

```bash
python scripts/validate_sft_data.py \
  --train data/stardew/sft/train.jsonl \
  --validation data/stardew/sft/validation.jsonl \
  --eval data/stardew/sft/eval.jsonl \
  --strict
```

Run the automated tests covering this pipeline:

```bash
python -m pytest -q tests/games/stardew
```
